## 0. Cómo se construye la BD hoy (orden de aplicación)

La BD **no se crea sola**: el backend solo sincroniza permisos (`permission.csv`)
al arrancar. Las tablas se aplican manualmente con `psql` en este orden:

```bash
psql -h $DB_HOST -U $DB_USER -d $DB_NAME -f db/schema.sql          # 1. Seguridad/perfiles
psql -h $DB_HOST -U $DB_USER -d $DB_NAME -f db/seed.sql            # 2. Datos iniciales (admin)
psql -h $DB_HOST -U $DB_USER -d $DB_NAME -f db/migrations/002_fuel.sql  # 3. Combustible
psql -h $DB_HOST -U $DB_USER -d $DB_NAME -f db/migrations/004_security_completion.sql  # 4. person.department + user.first_name/last_name/email UNIQUE (independiente de la 003, YA APLICADA)
# psql ... db/migrations/003_fuel_english.sql   # 5. Modelo en inglés + fuel_pesada — POSPUESTA, no aplicar sola (ver nota arriba)
```

> ⚠️ **003_fuel_english.sql** renombra columnas de `vehicle`, `fuel_carga` y `fuel_foto`.
> Debe aplicarse **junto** con la actualización de `backend/config/queries.yaml`, las clases
> BO (`vehiculo.js`→`Vehicle`, `carga.js`→`Refuel`) y el frontend (`fuelService.js` + páginas
> fuel). Aplicarla con la BD vieja y el backend viejo rompe tx 81-90.

- Credenciales: variables del `.env` del backend (`DB_HOST`, `DB_PORT`, `DB_USER`, `DB_PASSWORD`, `DB_NAME`).
- La migración `001` **no existe** (la numeración arranca en 002; `schema.sql` es la base).
- Esquema usado por completo: **`public`**.
- Convención aplicada en todo el proyecto:
  - `id BIGINT GENERATED BY DEFAULT AS IDENTITY` siempre.
  - Soft-delete: columna `deleted_at TIMESTAMPTZ` (no se borra físicamente salvo decisiones puntuales).
  - Auditoría: `created_at` / `updated_at` con `DEFAULT NOW()`.
  - `created_by BIGINT REFERENCES "user"(id)` en tablas de negocio que registran quién hizo la acción.
  - Checks e índices sobre columnas de búsqueda.

### 3.5 Matriz de permisos (subsistema → clase → método → perfil)

El motor de permisos modela la arquitectura de `permission.csv`:

- `subsystem` — módulos (ej. `Security`, `Fuel`, `Users`…): `id`, `name` (UNIQUE), `description`.
- `class` — clases de negocio (ej. `Person`, `Carga`…): `id`, `name` (UNIQUE), `description`.
- `method` — métodos (ej. `createCarga`…): `id`, `name` (UNIQUE), `description`.
- `subsystem_class` — N:M subsistema↔clase: `id`, `subsystem_id` (FK), `class_id` (FK), `uq(subsystem_id, class_id)`.
- `class_method` — N:M clase↔método: `id`, `class_id` (FK), `method_id` (FK), `uq(class_id, method_id)`.
- `method_profile` — N:M método↔perfil (es la matriz de permisos efectiva): `id`, `method_id` (FK), `profile_id` (FK), `uq(method_id, profile_id)`.
- `transaction` — registro de la transacción (alcance subsistema-clase-método):
  `id`, `subsystem_id` (FK), `class_id` (FK), `method_id` (FK), `created_at`, `updated_at`, `uq(subsystem_id, class_id, method_id)`.
  Es la tabla que el backend sincroniza desde `permission.csv` al arrancar (function `syncPermissions`): la **columna `id` del CSV = ID de la transacción** que usa el front (`transaction_id`).

### 3.6 Menús y opciones por perfil (navegación)

- `option` — opción de navegación: `id`, `name` (UNIQUE), `description`.
- `option_profile` — N:M opción↔perfil: `id`, `profile_id` (FK), `option_id` (FK), `uq(profile_id, option_id)`.
- `menu` — menú: `id`, `name`, `description`, `subsystem_id` (FK → `subsystem`), `uq(name, subsystem_id)`.
- `option_menu` — N:M opción↔menú: `id`, `option_id` (FK), `menu_id` (FK), `uq(option_id, menu_id)`.

> Estas tablas de navegación están definidas pero **aún no son pobladas** por el frontend (el sidebar es estático hoy).

## 5. Tablas de la fase backend

### 5.1 `fuel_pesada` — Llenados de flota pesada (pesada)

> **Creada por `003_fuel_english.sql`** (aplicada de forma coordinada con backend + frontend).
> **Medida única valor+tipo** (no hay odómetro en pesada; hay unidades que se rigen por horas).

```sql
CREATE TABLE public.fuel_pesada (
  id BIGSERIAL PRIMARY KEY,
  transaction_no VARCHAR(40),          -- nomenclatura / id de transacción (la entrega el usuario)
  vehicle_id BIGINT NOT NULL REFERENCES public.vehicle(id),
  filled_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  requester VARCHAR(120),              -- solicitante: distinto al responsable de liviana
  fuel_type VARCHAR(20) NOT NULL DEFAULT 'gasoil',
  measurement_value NUMERIC(10,1),     -- valor de la medida (km u horas)
  measurement_type VARCHAR(10) NOT NULL DEFAULT 'km',  -- 'km' | 'horas'
  gallons NUMERIC(10,2) NOT NULL,
  notes TEXT,
  created_by BIGINT REFERENCES public."user"(id),
  created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  deleted_at TIMESTAMPTZ,
  CONSTRAINT ck_fuel_pesada_gallons_positive CHECK (gallons > 0),
  CONSTRAINT ck_fuel_pesada_measurement_type CHECK (measurement_type IN ('km', 'horas'))
);
```

Índice: `idx_fuel_pesada_vehicle (vehicle_id, filled_at DESC)`.

- Fotos opcionales: decidir si se generaliza `fuel_foto` (columna `pesada_id`) o se crea `fuel_pesada_foto`.
- Conversión: `liters = gallons × 3.78541` (solo visualización).

### 5.2 `fuel_tanque` y `fuel_tanque_movimiento` — Tanque de gasoil (fase 2, pendiente)

> SQL de referencia, todavía **no aplicado** (fase 2). Nombres en inglés (mismo criterio).

```sql
CREATE TABLE public.fuel_tanque (
  id BIGSERIAL PRIMARY KEY,
  code VARCHAR(20) UNIQUE NOT NULL,
  name VARCHAR(100) NOT NULL,
  capacity_liters NUMERIC(10,2) NOT NULL,
  min_level_alert_liters NUMERIC(10,2) NOT NULL DEFAULT 0,
  is_active BOOLEAN NOT NULL DEFAULT TRUE,
  created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  deleted_at TIMESTAMPTZ
);

CREATE TABLE public.fuel_tanque_movimiento (
  id BIGSERIAL PRIMARY KEY,
  tank_id BIGINT NOT NULL REFERENCES public.fuel_tanque(id),
  type VARCHAR(10) NOT NULL,           -- 'in' (abastecimiento) | 'out' (despacho); UI muestra Entrada/Salida
  amount_liters NUMERIC(10,2) NOT NULL,
  referent_type VARCHAR(20),           -- 'pesada' | 'manual' | ...
  referent_id BIGINT,                  -- fuel_pesada.id si el despacho fue un llenado pesado
  note TEXT,
  created_by BIGINT REFERENCES public."user"(id),
  created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
```

- Nivel = Σ entradas − Σ salidas (se **calcula** al consultar, no se almacena).
- Alerta cuando `nivel ≤ nivel_min_alerta_litros`.

## 6. Diagrama de relaciones (resumen)

```
person ──────< user ──────< user_profile >────── profile
                          (usuario N:M rol)

profile >──── method_profile >──── method >───── class >──── subsystem
        (permisos: método disponible por perfil)

subsystem >──── menu >──── option_menu >──── option
profile >──── option_profile >──── option      (navegación por perfil)

vehicle ──────< fuel_carga ──────< fuel_foto
        1            N               N
vehicle ──────< fuel_pesada ───────(fotos opcionales)
vehicle ──────< (fleet_type: liviana | pesada)
person ──────< fuel_carga.responsible_id     (fase backend)
user  ──────created_by──> fuel_carga / fuel_pesada (auditoría)
```

### 6.1 Notas de cardinalidad

| Relación | Tipo | Regla |
|---|---|---|
| `person` 1—N `user` | 1:N | `person_id` ON DELETE SET NULL |
| `user` N—M `profile` | N:M | vía `user_profile` (RESTRICT) |
| `profile` N—M `method` | N:M | vía `method_profile` (matriz de permisos) |
| `vehicle` 1—N `fuel_carga` | 1:N | FK `vehicle_id` |
| `fuel_carga` 1—N `fuel_foto` | 1:N | FK `refuel_id` |
| `user` 1—N `fuel_carga.created_by` | 1:N | auditoría (NULL permitido) |
| `person` 1—N `fuel_carga.responsible_id` | 1:N | **fase backend** |

## 7. Datos iniciales (seed.sql)

| Dato | Valor |
|---|---|
| Persona | `ADMIN-00001` — Administrador Sistema |
| Usuario | `admin01` / `admin01@fullpetro.com` / **Admin1234** (hash bcrypt) |
| Perfil | `admin` — Administrador del sistema |
| Vinculación | `user_profile` admin01 ↔ admin |

> El perfil `admin` se **re-sincroniza** con `backend/config/permission.csv` al arrancar el backend (cada fila del CSV crea/actualiza la cadena subsystem→class→method→method_profile→transaction).
>
> **Importante (corregido 31/08/2026):** la columna `id` del CSV es solo un identificador de lectura para humanos — **no** determina el `transaction_id` real. El id real lo asigna Postgres por autoincremento (`transaction.id GENERATED ... AS IDENTITY`) en el momento en que `syncPermissions()` inserta esa combinación `subsystem+class+method` por primera vez (orden de aparición en el archivo, no el número escrito). Los rangos 1-90 coinciden con el CSV porque así se insertaron originalmente en una BD nueva; para cualquier fila **nueva** hay que verificar el id real después de sincronizar (`SELECT id, sub_system, class_name, method_name FROM transaction ...`) antes de asumir que coincide con lo escrito en el CSV.
